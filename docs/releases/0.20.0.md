Twentieth release. The project closes every finding from the 0.19.0 walkthrough and the full seven-engine feature tour: backup artifacts are collision-proof, the current Oracle and PostgreSQL clients are validated before work starts, public API/CLI/webhook contracts are clearer, and the operator console remains usable at constrained content widths.

## What is new

- Local backup artifacts now live at `<targetId>/<executionId>/<file>`, matching the identity boundaries already used by remote object keys. A new backup refuses to overwrite any existing artifact.
- The optional Oracle pack builds with Instant Client 23.26, supplies the `libaio.so.1` ABI it requires, checks all three ELF clients during image build and tests the shared Data Pump staging directory in both directions.
- The base image ships PostgreSQL 17 `psql`, `pg_dump` and `pg_restore`. Target testing compares the server major with the configured dump client and rejects an unsupported newer server before a backup begins.
- API request validation returns independent field errors together, and omitted `verifyAfterBackup` values now use the documented `false` default.
- The CLI's default text output uses readable tables and key/value sections; JSON envelopes remain available explicitly for automation.
- Generic webhooks use lossless ISO-8601 UTC `occurredAt` values and identify the actual receiving channel on every test and lifecycle delivery.
- Targets and Storage choose labelled cards or dense tables from their available container width. The console also fixes credential-manager autofill boundaries, crowded page headers, Azure container wording and live cron descriptions.
- `docs/FEATURES.md` and the feature-tour media document every console, API and CLI flow across all seven engines, remote storage, notifications and restore verification.

## Behaviour changes

- New local artifacts use `BACKUP_DIR/<targetId>/<executionId>/<file>`. Existing flat artifacts are not migrated; their stored locators remain valid for download, checksum verification, restore and deletion.
- `verifyAfterBackup` defaults to `false` when it is omitted from API requests. Validation failures can contain multiple ordered field errors instead of stopping after the first.
- Human-readable CLI text is now the default. Scripts must use `--output json` when they depend on the stable API envelope rather than terminal-oriented output.
- Webhook `occurredAt` is an ISO-8601 string, and `channel.id` plus `channel.name` are no longer `null` for backup, restore or verification lifecycle events. The surrounding JSON structure is unchanged.
- Targets and Storage render labelled cards whenever their own content width is below 1540px; at or above that width they render the existing table. Mobile card behaviour is unchanged.
- Chrome no longer treats database target fields as operator sign-in credentials. Storage and schedule forms use provider-accurate wording and entered-cron descriptions.
- Oracle connection testing now requires the application-to-server and server-to-application staging probes to succeed and reports numeric ownership/mode details when shared staging permissions fail.

## Upgrading from 0.19.0

- No database migration or mandatory configuration change is required. Existing targets, schedules, policies, channels, executions and artifacts remain valid.
- Container deployments can pull `ghcr.io/hoangluongtran0309/database-backup-utility:0.20.0`; source deployments should rebuild so PostgreSQL 17 clients and the current runtime packages are present.
- Local backup directories will gain target and execution subdirectories only for new backups. Do not move old flat artifacts: the application continues to use their stored paths without migration.
- Automation that parses CLI output should add `--output json`. Interactive use can keep the new default text output.
- API clients may omit `verifyAfterBackup`; the effective value is `false`. Clients should be ready to display or process every entry in a multi-error validation response.
- Oracle operators can build `Dockerfile.oracle.example` with Instant Client 23.26 Basic/Basic Light, SQL\*Plus and Tools archives. Keep those licensed files outside the repository, and retain the documented shared group or equivalent ACL for the Data Pump staging mount.
- Existing encryption keys, operator credentials, database targets and storage/notification configuration require no changes.

## Scope and limitations

The published GHCR product remains the base Linux AMD64 image. Oracle and SQL Server application packs and the SQL Server verification image remain operator-built because their vendor components are not redistributed. PostgreSQL packaging is pinned to client major 17; a newer source server requires a compatible custom client, and restore compatibility with an older destination is still the operator's responsibility. Oracle staging still requires coordinated numeric group ownership or equivalent ACLs across containers. This release does not add physical backups, incremental or differential chains, point-in-time recovery, cross-engine conversion or automatic migration of artifact files.
